The interface

Write a Policy

Your submission is a Kaggle notebook. In it you subclass the policy base class supplied by the evaluation gateway, and hand your class to the inference server. The class is initialized once per scenario with building_meta_data and action_spec. At each step the gateway calls get_action(obs) to obtain the discrete on/off commands and continuous setpoints for the current building. Because the metadata carries the action dimensions, one class handles any building. Your notebook contains no scenario list and no rollout loop; the gateway owns the simulator and drives it.

submission.ipynb 
from typing import Dict, Any
import numpy as np

from kaggle_evaluation import smart_buildings_inference_server


class TransferPolicy(smart_buildings_inference_server.Policy):
    def __init__(self, building_meta_data, action_spec):
        super().__init__(building_meta_data, action_spec)
        self.n_discrete = building_meta_data["n_discrete_action"]
        self.n_continuous = building_meta_data["n_continuous_action"]

    def get_action(self, obs: np.ndarray) -> Dict[str, Any]:
        return {
            "continuous_action": np.zeros(self.n_continuous, dtype=np.float32),
            "discrete_action": np.zeros(self.n_discrete, dtype=np.int32),
        }


smart_buildings_inference_server.SmartBuildingsInferenceServer(TransferPolicy).run()

Reference policy. A minimal policy that reads its action dimensions from the building metadata and returns a zero action. Replace get_action with your learned policy. The class is named TransferPolicy to match the starter kit and the starter notebook. A complete, runnable version is the TransferPolicy Notebook on the Kaggle Code tab.

How to submit

From starter notebook to leaderboard

You upload one notebook to Kaggle. Nothing else is submitted.

  1. Copy the starter notebook

    Open the TransferPolicy Notebook on the Kaggle Code tab and copy it. It already imports the gateway and runs end to end.

  2. Write your policy

    Replace the logic in get_action. Keep the two signatures, __init__(building_meta_data, action_spec) and get_action(obs), and keep the subclass of smart_buildings_inference_server.Policy. Load any model weights in __init__ from a Kaggle Dataset attached to the notebook.

  3. Test it in the notebook

    Running the notebook yourself plays one public example scenario, so you can check that your policy loads and runs. To score against all 30 training scenarios, use evaluate.py and score_leaderboard.py from the starter kit.

  4. Submit

    Save a version of the notebook and submit it on the competition page. Kaggle re-runs the same notebook against the hidden test scenarios. You do not change any code between testing and submitting.

Guidelines

  • A fresh policy is built for every scenario, so no state carries from one scenario to the next.
  • Time limits: 15 minutes for the first step of each scenario, for loading a model, then 60 seconds per step. The whole submission must finish within one Kaggle session.
  • Return actions inside the action space bounds. Out-of-range actions are rejected.
  • Make sure every action is a finite number. A NaN is not caught by the bounds check and corrupts the rest of the episode.
  • Read action and observation positions from the building metadata. Do not hardcode them.
  • Do not reference held-out configurations or weather. Doing so is disqualifying under the competition rules.

Building metadata

How one policy adapts to any building

The metadata is what lets a single policy condition its control on the specific building it operates, rather than rely on a fixed input layout.

Action structure

The number of discrete and continuous actions, and the indices of the temperature, pressure, recirculation, water, and per-zone (damper and reheat) setpoints within the continuous action vector.

Observation structure

The observation field names and the indices of the zone temperature sensors.

Building layout

The floor plan, the zone map, the assignment of zones to AHUs, and the number of floors.

Schedule & comfort targets

Morning and evening start hours, the comfort window during work hours, the eco window for unoccupied periods, the time zone, and the holiday calendar.

Normalization

Observation and action normalization metadata that place raw sensor readings and setpoints on a common scale.

Why it matters

Because the floor plan, zone map, and zone-to-AHU assignments are delivered for every building, a policy can parse each building's structure and adapt, which is exactly the capability the competition rewards.
